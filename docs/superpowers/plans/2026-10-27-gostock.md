# GoStock Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ferramenta web de decisão de estoque GoBeauté: diagnóstico, plano de compras 01/10–29/12/2026 montado por código e ajustado por um agente de IA (Groq), sugestões de liquidação, upload de CSVs. Publicada no Vercel.

**Architecture:** Núcleo puro em TypeScript (`src/core/`) que transforma CSVs em um `Dataset` agregado por SKU e, a partir dele, gera plano, curva de serviço e liquidações. O núcleo roda em script local (dados padrão → `src/data/dataset.json`), em Web Worker (upload) e no servidor (agente). O agente (`src/agent/`) só age por ferramentas que chamam o núcleo e o validador; rota `/api/agent` stateless. UI Next.js App Router com 6 telas.

**Tech Stack:** Node 24, Next.js 16 (App Router) + TypeScript strict, Tailwind, Vitest 4, papaparse 5, recharts 3, groq-sdk 1, tsx (scripts).

**Spec:** `docs/superpowers/specs/2026-10-27-gostock-design.md` (+ regras em `CLAUDE.md`).

> **Desvios registrados (27/10):** a execução das Tasks 1–12 tomou decisões que alteram este plano: `budgetCurve`, prioridade só dentro da janela, falha parcial do agente, ferramenta `aplicar_ajustes`, contexto inicial do agente, modelo `openai/gpt-oss-120b` e migração pendente para Claude Haiku. Detalhes na seção 9 do design e no `CLAUDE.md`. Onde houver conflito, o código e esses documentos prevalecem.

## Global Constraints

- O agente nunca produz número próprio; todo número exibido vem de função do núcleo. Texto final do agente passa pelo `numberGuard` (Task 11).
- Regras validadas em código (`src/core/plan/validate.ts`): quantidade múltipla do lote (`moq × unidadesPorUnidadeCompra`), `cx 12 un` = 12 unidades, teto de orçamento, desconto ≤ 0,40, sem recompra de descontinuado, emissão entre `windowStart` e `windowEnd`.
- Valores padrão de `Config` (copiar exatamente): `referenceDate: "2026-09-29"`, `historyStart: "2025-04-01"`, `budget: 1970000`, `windowStart: "2026-10-01"`, `windowEnd: "2026-12-29"`, `capitalCostYear: 0.18`, `storageCostMonth: 0.012`, `maxDiscount: 0.4`, `serviceTarget: 0.98`, `reviewDays: 30`, `idleCoverageDays: 180`, `tiers: { A: 0.98, B: 0.95, C: 0.90 }`, `markdownPriceShare: 0.5`, campanhas `bf` ("Black Friday", 2026-11-20 → 2026-11-30, ano anterior 2025-11-20 → 2025-11-30) e `natal` ("Natal", 2026-12-01 → 2026-12-22, ano anterior 2025-12-01 → 2025-12-22).
- `src/core/**` não importa nada de `next`, `react`, `fs`, `window` ou `document`.
- `src/data/dataset.json` (commitado) não contém os campos `unitCost`, `price` nem histórico diário. Histórico só semanal.
- `case_estoque/`, `*.pdf`, `.env*` nunca entram no git (já no `.gitignore`).
- Texto de UI e do agente em pt-BR. Identificadores em inglês segundo o glossário do `CLAUDE.md`.
- Datas no núcleo são strings `YYYY-MM-DD`. Aritmética de data só via `src/core/dates.ts`.
- Testes usam fixtures sintéticas em `tests/fixtures/`, nunca `case_estoque/`.
- `GROQ_API_KEY` só no servidor. `GROQ_MODEL` opcional, padrão `"llama-3.3-70b-versatile"`.
- Corpo de requisição ao servidor ≤ 4,5 MB: o cliente envia ao agente o dataset sem `weekly`/`daily` (`stripForAgent`).

## Review Focus

1. **Groq falha no meio** (429, timeout, chave ausente) → o plano base permanece, a UI mostra "Agente indisponível, exibindo plano base" e nada quebra. Teste em Task 12 (`runAgent` com cliente falso que lança erro 429).
2. **Upload com CSV inesperado** (BOM, separador `;`, coluna faltando, número com vírgula decimal) → erro em pt-BR nomeando arquivo e coluna, sem travar. Testes em Task 1 (`loadDataset`).
3. **Ferramenta do agente chamada com dado inválido** (SKU inexistente, `lots` 0/negativo/fracionário, data inválida) → retorna erro estruturado ao modelo, sessão intacta. Teste em Task 10.
4. **SKU sem venda recente, recém-lançado ou com todos os dias censurados** → nenhum `NaN`/`Infinity` no dataset; cobertura sem demanda vira `9999`. Teste em Task 6 (varre o dataset do fixture).
5. **Aprovações salvas no navegador de outro dataset** (depois de upload ou nova versão) → descartadas, nunca aplicadas ao plano errado. Teste em Task 14 (`loadApprovals` com `datasetId` diferente).
